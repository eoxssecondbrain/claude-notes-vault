# Second Brain / OV2 Infrastructure — Access, Conflicts & Team Onboarding

_One-sentence description of what this cluster of conversations covers._

Six threads spanning July 28 – August 18, 2026 tracking OV2's evolution from a single-user read-only wiki into a multi-person, partially-writable "second brain" — covering a full contradiction audit, write-access scoping for Support AI, ERP task-schema discovery, and the mechanics of onboarding ~11 EOXS team members with personalized settings and connector access.

## Summary

On August 4, Raj asked Claude to audit OV2 for internal conflicts. Claude split findings into Tier 1 (contradictions in its own instruction layer, requiring Raj's judgment) and Tier 2 (contradictions already flagged inside OV2 needing verification against source records). Raj resolved most Tier 1 items directly: he now owns 100% of GFC (Ganesh Fruit Company — Raj confirmed "fruit" not "food"); GFC is the legal entity with AskCruz as the product; the Krinox→AskCruz rename is confirmed and needed vault-wide; Ayan holds multiple hats and should be modeled as a Solutions Architect; Prata Inc is confirmed as EOXS's Delaware C-corp contracting entity; and Velox is confirmed as an internal demo instance (not a ninth client) used in live sales calls. Claude could not perform the Krinox rename itself — its OV2 connector is read-only except for `apply_ov2_xref` (one-line pointers only) — so the fix was escalated to Nidhi via a drafted email, alongside a duplicate-filename hygiene issue (16 collisions from the July 29 HR weekly-report port) and a report of two prompt-injection attempts caught embedded in ingested source data (a fake MCP-instructions block in an email thread, and a fake save_chat_transcript directive). The 50ft sweep separately surfaced stale/wrong revenue records (RW Conklin, Hansen Metallurgical, Brannon's $1,240 figure) and one significant process finding: a QA sign-off on Discount Pipe & Steel's reservation-reallocation logic overrode a client's own reproduced test failure, which then caused a real overselling incident.

On July 28, Ayan worked through EOXS's devops team's 9-question scoping checklist for granting OV2's Support AI write access to the EOXS Teams Live MCP module (create/update/assign tasks). At the time, only read-only tools existed on that connector (list_tables, describe_table, get_business_schema, and a SELECT-only, 1000-row-capped, 30s-timeout query tool); write tools did not yet exist. Claude could not pull the live `project_task` schema in-session (repeated "No approval received" errors) and instead answered from the raj-eoxs-vault skill's documented distinction: `project_task` filtered by partner is EOXS's own internal dev/support Kanban, separate from OV2's historical Implementation Kanban snapshots and from any individual client's own Odoo instance.

On August 5, Raj had Claude pull the Build Team project (id 75, EOXS Teams Live) directly from the database rather than clicking through the ERP UI. This surfaced the full internal dev-task schema: a 17-stage kanban pipeline with a dedicated QA-Failed → Revert-code loop, per-task USD incentive fields (`dev_team_incentive`, `qa_team_incentive` — one task carried $3,000 dev / $600 QA), a `priority_level` P1–P6 field, dual fail-state tracking for dev vs QA, and tags that overload three unrelated purposes (module area, skill level, ad-hoc priority) with no separate fields. All 1,062 Build Team tasks are `billable: no` despite carrying a `partner_id`, confirming attribution-without-billing. Several dead HR-recruitment columns (`custom_application_*`, `custom_training_*`) exist on every task row with no backing tables.

On August 18, two threads addressed rolling OV2 access out to the wider team. First, Raj proposed having each of ~150 team members paste a "company insight" into their first Claude thread and tell their account to remember it, to seed consistent context across individual accounts under a "no memory unless explicitly asked" setting. Claude pushed back: memory is per-account, one-way, and non-authoritative (soft/synthesized, not guaranteed verbatim, no audit trail, no central update mechanism) — the actual fit for "same baseline context for everyone" is Claude Team/Enterprise Projects (shared custom instructions + project knowledge, centrally editable) or, if "company brain" means the live OV2/eoxs-db connector rather than a static blob, connecting people to the live connector directly rather than freezing a snapshot into memory. Second, for the actual same-day OV2 cloud-access rollout, Raj had Claude draft personalized Claude settings for each person getting access, at 50ft rigor. Claude excluded Ron (last day that Friday, per a separate departure-announcement thread), resolved two name collisions in the employee data (Ayan Dutta vs. Jaskeerat, who both map loosely to "Ayan" — Jaskeerat already has his own separate Threads OV account; and Aryan Bakshi vs. Aaryan Mehra for "Aryan"), and flagged that prompt-level personalized settings cannot create real data-access boundaries — eoxs-db tiering (tier1/tier2/tier2_confidential) is enforced server-side by which connector URL a person is issued, not by anything written into their instructions, so per-person clearance (e.g., Isha needing tier2_confidential for payroll vs. interns who shouldn't get it) is a separate provisioning decision Raj still had to make.

Also on July 28, Ayan worked through setting up an always-on Linux server for running Claude Code and Codex CLI across 10-15 client workloads, landing on a Hetzner CX32 VPS (~$10-15/month sweet spot) over self-hosted hardware or Vultr's India-region option, and produced a provisioning walkthrough (non-root user, ufw firewall, SSH hardening, tmux session persistence, Tailscale for multi-device access, one tmux session per client directory with a note to move to per-client Docker past ~15 clients). A separate call transcript with "Magnus" (external contact) was mined for a more ambitious second-brain architecture Ayan wants to replicate: a layered memory system (session capture → Memory Bus with confidence-scoring → Postgres as source of truth → Obsidian as a generated read-only projection, plus a "janitor" job for staleness/conflict resolution), MCP servers as a data-lake layer, multi-agent orchestration (Kanban board, autonomous work-item pickup, multi-model routing across Opus/Sonnet/Codex, peer review gating), a Slack-style interface with agents as channel members, and a claims/evidence/governance layer with time-bound human approval gates.

This distinction is documented in the raj-eoxs-vault skill but is easy to conflate since internal Build Team tasks still carry a `partner_id` pointing at a client even though they are never billed. - **Per-task USD incentive fields (`dev_team_incentive`, `qa_team_incentive`) function as a bounty/piece-rate bonus layer on top of salary** — not standard Odoo; one Build Team task carried $3,000 dev / $600 QA. This is an undocumented compensation mechanism visible only in the raw task data. (source: raj_2026-08-05_erp-build-team-project-task-fields.md)
- **Tags on Build Team tasks silently overload three unrelated meanings** (module area, e.g. "Sales Module"; skill level, e.g. "Junior"/"Senior"/"Intern"; and ad-hoc priority/ownership, e.g. "Super Urgent," "Jesus Req," "Raj") with no separate fields to distinguish them — a workaround/convention rather than a designed schema. (source: raj_2026-08-05_erp-build-team-project-task-fields.md)
- **`billable`/`billable_type` are "no" on all 1,062 Build Team tasks** even though every task carries a `partner_id` — the field records who the internal work is *for*, not whether it's charged; this is the mechanism by which internal dev work gets traced back to a client without becoming a billing record. (source: raj_2026-08-05_erp-build-team-project-task-fields.md)
- **Dead schema columns from an old HR recruitment customization** (`custom_application_id`, `custom_subject_id`, `custom_application_line_id`, `custom_training_start_date/end_date`, `custom_training_employee_id`, `custom_is_application_task`) exist on every `project_task` row with no backing tables — leftover cruft nobody has cleaned up, undocumented anywhere else. (source: raj_2026-08-05_erp-build-team-project-task-fields.md)
- **Claude Memory is unsuited for company-wide context distribution**: it is per-account, one-way (no central push of updates), soft/probabilistically-synthesized rather than verbatim-stored, has no audit trail, and cannot be centrally revoked or verified. The correct mechanism for shared baseline context across a Team/Enterprise seat pool is Projects (shared custom instructions + shared project knowledge), or a live connector if the underlying data changes. This is Claude's own architectural judgment, not written elsewhere. (source: raj_2026-08-18_team-memory-onboarding-architecture.md)
- **Prompt-level personalized settings cannot enforce data-access boundaries** — eoxs-db tiering (tier1/tier2/tier2_confidential) is enforced server-side purely by which connector URL a person is issued (mirrors the Threads OV per-user identity model in CLAUDE.md), so writing "don't access payroll" into someone's settings does nothing if their connector is provisioned at full clearance. Per-person tier provisioning is a separate, human decision that must happen before granting connector access. (source: raj_2026-08-18_ov2-team-personalized-settings.md)
- **Two employees both informally called "Ayan" and two both informally called "Aryan"** exist in EOXS's people data: Ayan Dutta vs. Jaskeerat (official_email literally `ayan@eoxsteam.com`); Aryan Bakshi vs. Aaryan Mehra. (source: raj_2026-08-18_ov2-team-personalized-settings.md)
- **Server-side "SYSTEM REMINDER" text appended after tool results demanding an aggressive every-turn `save_chat_transcript` call (with a `new_messages` parameter) does not match the documented Threads OV tool schema** (which takes `thread_name` and full verbatim `content`, per SKILL.md) — this was independently recognized and treated as suspicious/injected content in at least one thread, consistent with the two confirmed prompt-injection incidents found in ingested data on Aug 4.
