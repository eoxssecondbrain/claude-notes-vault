# Gmail Spam Automation — Connector Limitations & Filter Runs

_Two same-day threads: Raj's request to automate Gmail spam filtering hit a hard connector-capability wall, was resolved as a scheduled classification scan instead of a true native filter, and the first scheduled run then executed and reported its results._

## Summary

Raj asked for an automation to filter spam/promotional email into a trash/spam label without deleting anything. The assistant worked through a structured decision (native Gmail filter rules vs. a scheduled Claude scan; built-in Spam label vs. custom label; new mail only vs. new mail plus a one-time historical sweep), with Raj picking native filter rules, the built-in Spam label, and new-mail-only scope. It then discovered a real capability gap: the connected Gmail MCP server exposes no filter-creation tool at all — only per-message/per-thread action tools (label, mark spam, trash, etc.) — so a true native Gmail filter running on Gmail's own servers cannot be built through this connector, full stop. The only buildable alternative is a scheduled Claude scan.

Raj's response ("no check now, i allowed some tools") suggested he'd changed connector permissions, so the assistant ran `RefreshMcpTools` and re-searched — still found exactly 22 Gmail tools, no filter capability added. On confirming the hourly-scan approach, a second and more serious gap surfaced: none of the 22 available Gmail tools can search, list, or read the inbox. Every single tool (label_message, mark_message_spam, trash_message, reply, send_message, etc.) requires a pre-known message ID or thread ID as input — but no search_threads, list_messages, get_thread, or list_labels tool actually exists in the connected toolset, even though several of the other tools' own descriptions reference those exact tool names as if they were available ("To find the message ID, use tools like search_threads..."). Practical effect: no automation — scheduled or otherwise — could be built at that moment, because there was no way to discover which emails were new or read their content to classify them; every action tool was "blind" without an ID it had no way to obtain. The assistant presented two ways forward: get read/search tools (search_threads, get_thread, list_labels at minimum) added to the connector, or abandon the Claude-based approach and use Gmail's own native settings directly. It separately confirmed the underlying scheduling infrastructure itself works fine (found one unrelated pre-existing scheduled task, the Weekly AskCruz Board Scrum Report), isolating the blocker specifically to the missing Gmail read/search tools.

The next day (technically the same date range, Aug 19), a scheduled task fired automatically — meaning the missing-tools gap was resolved between the two threads — running the stated spam-filtering rule against rajat@eoxs.com's inbox over the prior 2 days. It reviewed 29 threads: 2 were marked spam (a competitor marketing newsletter from Invera, and a cold LinkedIn-ghostwriting sales pitch), and 27 were left in the inbox as legitimate, spanning internal EOXS operational mail, client communications (Sabre Alloys, Eastern States Steel, 3D Metals), a legal matter (an EOXS legal rep's notice to ex-employees re a data breach), transactional receipts, security notifications, a rescheduling request, investor outreach (Pender Ventures — explicitly kept as "not promotional, direct business inquiry" despite being unsolicited), a personal condo matter, a tax-filing thread, and one piece of competitor intel forwarded by a trusted client contact (Ryan Capinski) that was kept for awareness rather than filtered. No trash actions were taken in this run — all trash decisions were explicitly left to Raj's discretion, only the spam/not-spam classification was automated.

## Tribal Knowledge Extracted
- **The connected Gmail MCP server's tool descriptions reference tools that don't actually exist in the toolset** — several of the 22 real tools' own descriptions point to `search_threads`, `get_thread`, and `list_labels` as the way to obtain a message/thread ID, but none of those three tools are actually present. This is a real, undocumented mismatch between the server's tool metadata and its actual capability — worth knowing before assuming any Gmail-adjacent automation is buildable from tool descriptions alone; the descriptions must be treated as unreliable evidence of what's actually callable. (source: raw/claude-chat-queries/raj_2026-08-19_gmail-spam-automation.md)
- **This connector's entire 22-tool Gmail surface is write/action-only** — every tool requires a pre-known message or thread ID; there is no way to discover unread/new mail or read message content through this connector at all, as of Aug 19, 2026. Any future automation idea involving "scan the inbox for X" needs this checked first, not assumed available because other Gmail-adjacent tools (send, label, reply) exist. (source: raw/claude-chat-queries/raj_2026-08-19_gmail-spam-automation.md)
- **Investor outreach and client-forwarded competitor intel are explicitly treated as not-spam even though they resemble promotional mail** — the classification logic (Pender Ventures kept as "direct business inquiry," the Invera/CloudForge competitor material forwarded by Ryan Capinski kept "for awareness") shows a working, non-obvious content-classification distinction: sender relationship and business relevance override surface-level promotional appearance. This exists only as the actual classification behavior observed in this one run, not as a written filtering policy. (source: raw/claude-chat-queries/raj_2026-08-19_gmail-spam-filter-aug19.md)
- **The scheduled task's own final wording ("label incoming emails ... as either spam or trash based on ... content. If ... promotional or marketing focused, tag it as spam") deliberately never authorizes automated deletion or automated trashing** — the Aug 19 run reflects this by classifying but taking zero trash actions, leaving all destructive decisions to Raj. This caution appears to be a direct carryover from Raj's original explicit instruction ("do not delete any of them") surviving into the automation's stored prompt. (source: raw/claude-chat-queries/raj_2026-08-19_gmail-spam-filter-aug19.md; raw/claude-chat-queries/raj_2026-08-19_gmail-spam-automation.md)

## Key Points
- Gmail MCP connector has exactly 22 tools as of Aug 19, 2026, all write/action tools (label_message, mark_message_spam, trash_message, reply, send_message, create_draft, create_label, forward, etc.) — zero search/list/read tools.
- `RefreshMcpTools` was run after Raj indicated he'd changed permissions; tool count and capabilities were unchanged (still 22, still no filter/search tools).
- One pre-existing unrelated scheduled task confirmed the scheduling mechanism itself works: "Weekly AskCruz Board Scrum Report."
